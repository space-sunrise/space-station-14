# SS14 Code Review

## Цель

Используй этот skill как operational playbook для ревью в `sunrise-station`.
Главная задача: находить реальные поведенческие риски, архитектурные нарушения и пробелы в проверках, а не делать пересказ diff 🙂

Если ревью становится слишком длинным и начинает упираться в окно контекста, подключай `ss14-code-review-context-compaction` и сжимай накопленное состояние ревью перед следующим проходом.

Для поиска контекста, связанного кода и быстрых read-only проходов по большим diff используй sub-agent `Explore`. Это особенно полезно, когда затронуто несколько подсистем или когда неочевидно, где именно искать вызывающие пути и аналоги.

## Порядок подключения знаний

1. Сначала определи поверхность изменения: какие подсистемы, слои и типы файлов затронуты.
2. Затем активируй релевантные skills до детального анализа diff.
3. Только после этого формулируй findings.

Мини-карта выбора skills:

1. ECS-логика, компоненты, системы, entity lifecycle:
   `ss14-ecs-components`, `ss14-ecs-entities`, `ss14-ecs-systems`, `ss14-events`, `ss14-eventbus`.
2. Shared/server/client split, networking, component state, PVS, prediction:
   `ss14-netcode`, `ss14-prediction`, `ss14-pvs`.
3. Transform/physics/movement/relay/pullable:
   `ss14-transform-system-core`, `ss14-transform-system-api`, `ss14-physics-system-core`, `ss14-physics-system-api`, `ss14-virtual-controller-core`, `ss14-virtual-controller-api`, `ss14-matrix-transform-physics-sprite`.
4. UI/BUI/EUI/XAML/style:
   `ss14-ui-bui`, `ss14-ui-eui-and-ui-manager`, `ss14-ui-xaml`, `ss14-ui-styles-palettes-sheetlets`.
5. Appearance/sprite/shaders/overlays/audio/atmos:
   соответствующий `*-core` и `*-api` skill по конкретной подсистеме.
6. Прототипы, YAML, локализация, naming:
   `ss14-ecs-prototypes`, `ss14-localization-code`, `ss14-localization-strings`, `ss14-naming-conventions`.
7. Изменения в ванильных файлах, partial-расширения, migration-подход:
   `ss14-upstream-maintenance`.
8. Hot-path, аллокации, query-паттерны:
   `ss14-standard-optimizations`.
9. Тесты, тестовая архитектура и надежность assertions:
   `ss14-tests-authoring`, при integration-случаях также `ss14-tests-poolmanager`.

Если diff затрагивает несколько зон, активируй несколько skills. Не пытайся делать «универсальное» ревью без доменного контекста.

## Источник правды и границы доверия

1. Источник правды номер один: текущий diff и актуальный код вокруг него.
2. Источник правды номер два: релевантные skills, уже сверенные под этот репозиторий.
3. История git и старые решения используй только для восстановления intent, а не как автоматический эталон.
4. Старые фрагменты с TODO, hack и legacy-комментариями не считай best practice по умолчанию.
5. Если код и skill расходятся, сначала проверь свежесть факта; устаревший skill надо обновить сразу.

## Ментальная модель ревью

Думай о ревью как о четырех проходах:

1. `Scope`: что меняется фактически, какие инварианты обещает diff.
2. `Architecture`: соответствует ли решение паттернам SS14/Sunrise и выбранной подсистеме.
3. `Runtime`: не ломает ли изменение prediction, networking, event order, containers, transforms, PVS, serialization или performance.
4. `Evidence`: есть ли тесты, build-validation и минимально достаточные проверки под риск изменения.

Если на любом проходе находится потенциальная регрессия, формируй finding. Если видишь только stylistic preference без риска поведения, не раздувай ревью.

Если для любого прохода требуется много read-only поиска по крупной поверхности, сначала отправляй эту часть в sub-agent, а уже потом формируй выводы в основном ревью-потоке.

## Рабочий процесс ревью

### 1) Зафиксируй объект ревью

1. Определи, что именно ревьюится: PR, unstaged diff, staged changes, отдельный файл или конкретный коммит.
2. Внимательно прочитай формулировку пользователя и не расширяй объем ревью без запроса.
3. Если пользователь явно просит проверить только текущие изменения, staged changes, конкретный diff или набор файлов, ревьюй только эту поверхность.
4. Если пользователь просто просит `review`/`ревью` без уточнения области, по умолчанию считай базой основную ветку и ревьюй разницу между текущей веткой и `main`.
5. Если diff не дан явно, сначала собери список измененных файлов в выбранной области ревью.
6. Раздели файлы на группы: C#, YAML/prototypes, UI/XAML, localization, tests, assets.
7. Если файлов много или они распадаются на несколько подсистем, используй `Explore` для быстрого read-only triage: пусть он вернет карту файлов, ключевые entry points, связанные вызовы и зоны повышенного риска.

### 2) Построй карту риска

Проверь ранние сигналы, которые почти всегда повышают риск:

1. Изменения в `Content.Shared` почти всегда требуют проверки server/client-симметрии.
2. Изменения в `Content.Server` вокруг interaction, do-after, physics, transforms, containers или state-sync требуют проверки runtime-инвариантов.
3. Изменения в `Content.Client` часто скрывают prediction/UI/state-apply регрессии.
4. Изменения в ванильных файлах вне `_Sunrise`-папок требуют проверки на merge-risk и hook-minimization.
5. Изменения prototype ID, component fields, migration и localization keys требуют проверки всех ссылок, а не только самого файла.
6. Если карта риска неочевидна по самому diff, отправь в sub-agent задачу на поиск затронутых call sites, state paths, tests и смежных файлов.

## Sub-agent workflow

Используй sub-agent не для финального verdict, а для ускорения read-only этапов ревью.

Когда звать `Explore`:

1. Нужно быстро найти связанные файлы, usages, event flow или tests вокруг измененной подсистемы.
2. Дифф большой и размазан по нескольким директориям.
3. Нужно проверить, где еще используется prototype ID, state field, UI message или API, не засоряя основной поток десятками поисков.
4. Нужно восстановить архитектурный контекст перед формулировкой finding.

Что просить у sub-agent:

1. Только read-only исследование.
2. Четкий scope: какие файлы, подсистемы, типы рисков и какой уровень thoroughness нужен.
3. На выходе требуй короткий отчет:
   - какие файлы и пути важны;
   - какие инварианты или usage sites найдены;
   - какие зоны выглядят рискованными;
   - какие тесты или аналоги стоит проверить.

Что не отдавать sub-agent:

1. Финальную формулировку findings пользователю.
2. Итоговую severity-классификацию без собственной валидации.
3. Решение о том, valid ли finding, без проверки основным ревью-потоком.

Считай sub-agent инструментом сжатия поиска, а не заменой reviewer judgment.

### 3) Проведи архитектурный проход

Проверь, что решение совпадает с принятыми паттернами:

1. Event-driven gameplay следует схеме `OnEvent -> TryDo -> CanDo -> Do`, где `CanDo` не мутирует состояние.
2. Публичные методы остаются безопасными и не полагаются на то, что вызывающий уже все проверил.
3. В non-Sunrise или иных сторонних/ванильных файлах изменения должны быть минимальными и явно помеченными соответствующими комментариями `edit start/end` или `added start/end`, если правка не является полностью новой isolated-единицей.
4. Если видишь, что заметную часть логики можно безболезненно вынести из стороннего файла, отмечай это как review concern: для этого репозитория merge-risk важнее локальной "красоты".
5. В partial/extension-сценариях большая часть новой логики должна жить в проектных `_Sunrise`-папках, а не размазываться по ванильным файлам.
6. Когда это уместно, новая проектная часть должна повторять исходный путь файла, но под префиксом `_Sunrise`, чтобы структура оставалась предсказуемой.
7. Для расширения существующих типов предпочитай `partial`-классы и точечные хуки вместо переписывания крупных ванильных блоков.
8. Для сетевых изменений есть явный путь: событие/состояние/dirty/PVS/prediction.
9. Для YAML-изменений используется наследование, migration или минимальные edit-маркеры вместо тяжелого копипаста ванильных сущностей.

### 4) Проведи runtime-проход

Проверяй не только локальную корректность, но и побочные эффекты:

1. Не нарушен ли порядок событий или инициализации.
2. Не добавлены ли side-effects в `Can*`, `Resolve*`, state-apply или validate-ветки.
3. Не появилась ли логика, которая на клиенте и сервере живет по разным правилам без явного gating.
4. Не пропущены ли `Dirty`, component state, `RaiseLocalEvent`, PVS override, prediction hook или cleanup.
5. Не возникает ли риск nondeterminism из-за случайности, времени, магических тиков или скрытой зависимости от порядка entity iteration.
6. Не добавлен ли лишний hot-path cost: LINQ, лишние alloc, повторные resolve/query, тяжелые поиски в update/event loops.

### 5) Проведи data/content-проход

1. Для prototype/YAML проверь parent-chain, корректность полей, категории, скрытие из spawn menu, миграции и все внешние ссылки на ID.
2. Для localization проверь, что новые строки реально существуют и вызываются через корректный паттерн `Loc.GetString(...)`.
3. Для UI проверь, что state-message контракт между server/client симметричен и не ломает lifecycle окна.
4. Для appearance/sprite/visualizer проверь, что визуальное состояние не живет только локально без network-backed data.

### 6) Проведи evidence-проход

1. Спроси себя: какой минимальный тест должен был бы упасть, если здесь есть баг?
2. Если тестов на новую механику нет, не считай это автоматически блокирующим дефектом, но обязательно пометь как testing gap и предложи добавить test coverage.
3. Если в проекте уже есть релевантные тесты, проверь их applicability даже если сами тестовые файлы не менялись: изменение production-кода может сделать их неверными, сломанными или недостаточными.
4. Для fixed bug проверь, есть ли воспроизводимый regression test или хотя бы reason, почему тест написать сложно.
5. Если изменение player-visible, проверь нужен ли changelog в PR-описании.

### 7) Сформулируй findings

Порядок ответа:

1. Findings first, по severity сверху вниз.
2. Для каждого finding укажи:
   - где проблема;
   - какой контракт или инвариант нарушен;
   - к чему это приведет в runtime;
   - чего не хватает для закрытия риска.
3. Summary и overview давай только после findings и только кратко.
4. Если findings нет, скажи это явно, но перечисли остаточные риски и пробелы в тестах.

## Шкала severity

Используй единую шкалу и по возможности называй severity явно:

1. `critical` — сломанные фичи, гарантированные build/runtime ошибки, отсутствующая или сломанная серверная валидация, высокая вероятность краша, возможность недобросовестного игрока абузить механику через некорректные данные.
2. `high` — существенные логические ошибки механики, потенциальные абузы и edge-cases, сломанная верстка UI, заметная некорректность пользовательского поведения без тотального отказа системы.
3. `medium` — использование `[Obsolete]`, плохие практики, рискованные решения, спорные архитектурные места, лишние аллокации и иные оптимизационные/поддерживаемые проблемы среднего веса.
4. `low` — малозначимые версии `medium`: локальные шероховатости, слабые smells, мелкие улучшения качества, которые не выглядят срочными.
5. `style` — проблемы только со стилем кода, оформлением и читаемостью без явного behavioral-рискa.

Если замечание можно обосновать только как `style`, не повышай его искусственно до более высокой severity.

## Что считается хорошим finding

Хороший finding:

1. Привязан к наблюдаемой регрессии, а не к вкусу ревьюера.
2. Объясняет причинно-следственную цепочку.
3. Опирается на архитектурный контракт SS14/Sunrise.
4. Дает понятную точку проверки: тест, состояние, кейс, событие, режим prediction, вход в PVS и т.п.
5. Не требует от автора «догадаться», почему это важно.

## Паттерны хорошего ревью ✅

1. Сначала выбирать релевантные skills по diff, потом читать изменения детально.
2. Сначала точно зафиксировать поверхность ревью по запросу пользователя и не проверять лишнее без причины.
3. Для `Content.Shared` сразу искать server/client последствия и component state impact.
4. Для interaction/event-кода проверять схему `OnEvent -> TryDo -> CanDo -> Do`.
5. Начинать с инвариантов и runtime-поведения, а не со стиля.
6. Для ванильных и сторонних правок проверять, нельзя ли оставить только минимальный hook/comment-marked diff и вынести основную логику в partial/_Sunrise с зеркальным путем.
7. Для prototype-изменений искать все внешние ссылки на ID и migration-последствия.
8. Для hot-path кода оценивать аллокации, query-patterns и частоту вызова, а не только правильность результата.
9. Для фиксов UI/networking/prediction требовать доказательство server/client симметрии.
10. Отсутствие тестов отмечать как testing gap и предлагать добавить coverage, а существующие релевантные тесты проверять даже вне diff.
11. Формулировать findings как риск продукта или архитектуры, а не как «я бы написал иначе».
12. Отдавать большие read-only поиски и первичную карту связей в `Explore`, а основным потоком делать валидацию и финальный verdict.

## Анти-паттерны ревью ❌

1. Делать ревью без активации доменных skills и пропускать архитектурный контекст подсистемы.
2. Самовольно расширять поверхность ревью, если пользователь просил проверить только текущие изменения или конкретный набор файлов.
3. Ограничиваться чтением diff без проверки окружающего кода и вызывающих/вызываемых путей.
4. Писать замечание только потому, что код «некрасивый», без объяснения runtime-риска.
5. Игнорировать `Content.Shared`-изменения на том основании, что серверная часть «и так разберется».
6. Не замечать merge-risk при правке ванильных или сторонних файлов вне `_Sunrise`-структуры и без comment-маркеров.
7. Считать отсутствие теста багом само по себе, не связывая это с реальной стоимостью регрессии.
8. Игнорировать prediction/PVS/Dirty/state-apply только потому, что изменение выглядит локальным.
9. Давать расплывчатые формулировки вроде «может сломаться синхронизация» без механизма поломки.
10. Смешивать findings, вопросы и summary так, что автор не понимает приоритеты.
11. Принимать копипаст старого legacy-кода как доказательство корректности нового решения.
12. Засорять основной поток десятками низкоуровневых поисков там, где sub-agent мог вернуть компактную карту контекста.

## Практические примеры

### Пример 1: gameplay-event ревью через контракт `Try/Can/Do`

```csharp
private void OnUseInHand(EntityUid uid, ExampleComponent component, UseInHandEvent args)
{
    if (args.Handled)
        return;

    if (TryActivate(uid, component, args.User))
        args.Handled = true;
}

public bool TryActivate(EntityUid uid, ExampleComponent component, EntityUid user)
{
    if (!CanActivate(uid, component, user))
        return false;

    DoActivate(uid, component, user);
    return true;
}
```

Комментарий: на ревью проверяй, что `CanActivate` не меняет состояние, а `TryActivate` не полагается на внешнюю предварительную проверку. Если логика «успеха» размазана между `OnUseInHand` и `TryActivate`, это архитектурный smell.

### Пример 2: правильный фокус на upstream-risk

```csharp
// Sunrise added start - hook для кастомной логики
RaiseLocalEvent(uid, ref ev);
// Sunrise added end
```

Комментарий: если автор внес точечный hook в ванильный файл и вынес большую часть логики в project-specific partial/system, это обычно хороший знак. Если же diff переписывает большую ванильную ветку целиком без крайней необходимости, это сильный merge-risk finding.

### Пример 3: prototype review с проверкой всех ссылок

```yaml
- type: entity
  parent: AirlockBase
  id: AirlockCustomLocked
  components:
  - type: AccessReader
    access: [[CustomAccess]]
```

Комментарий: само наследование выглядит нормально, но ревью не заканчивается на этом. Проверь migration, спавнеры, loot, recipe, map entities и все остальные места, где старый ID мог остаться без замены.

### Пример 4: как должен выглядеть finding

```text
High: новое состояние компонента меняется на сервере, но не помечается dirty и не попадает в component state.
В результате клиентский UI останется на старом значении до полного ресинка или повторного открытия окна.
Нужен либо явный Dirty/component state update, либо объяснение, почему это состояние purely server-side.
```

Комментарий: здесь есть место, механизм поломки и ожидаемое исправление. Это полезный finding.

## Мини-чеклист перед завершением ревью

1. Найдены и активированы релевантные skills по затронутым подсистемам.
2. Объем ревью соответствует прямому запросу пользователя или дефолту `current branch vs main`.
3. Проверены server/shared/client последствия там, где это требуется.
4. Отдельно оценены upstream-risk, prediction/networking-risk и testing gaps.
5. Findings отсортированы по шкале `critical/high/medium/low/style` и опираются на поведение, а не на вкус.
6. Если findings нет, явно названы остаточные риски и непроверенные зоны.

## Правило расширения skill

1. Если в репозитории появится новая крупная подсистема с собственными инвариантами, не раздувай этот skill деталями API.
2. Добавляй сюда только review-specific decision tree и типовые failure modes.
3. Доменную механику выноси в отдельный `*-core` или `*-api` skill и ссылайся на него из карты выбора.
4. Если в процессе ревью выясняется, что существующий доменный skill устарел, обновляй его сразу: для этого репозитория это нормальное ожидаемое поведение.
