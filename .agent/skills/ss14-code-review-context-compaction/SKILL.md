# SS14 Code Review Context Compaction

## Цель

Используй этот skill, когда длинное ревью начинает упираться в окно контекста.
Задача skill: ужать накопленное состояние ревью так, чтобы не потерять findings, уже проверенные зоны, активированные skills и оставшийся план проверки 🙂

Этот skill не заменяет `ss14-code-review` и `ss14-code-review-quick`. Он помогает продолжать их безопасно, когда ревью стало слишком длинным.

Если часть истории была собрана через sub-agent, compact summary должен сохранять и результаты этих sub-agent проходов: что они подтвердили, что осталось open question и какой next pass из этого следует.

## Когда использовать

Используй skill, когда:

1. Ревью стало длинным и в него уже вошло много файлов, подсистем и промежуточных выводов.
2. Есть риск забыть, что уже проверено, а что нет.
3. Findings уже частично сформулированы, но анализ еще не завершен.
4. Нужно передать самому себе компактное состояние перед следующим проходом ревью.

Не используй skill для раннего анализа маленького diff: там compaction только добавит шум.

## Источник правды и границы доверия

1. Источник правды номер один: уже собранные факты ревью, а не длинный пересказ всех чтений подряд.
2. В compact summary должны попадать только подтвержденные наблюдения, а не сырые догадки.
3. Если hypothesis еще не проверена, маркируй ее как `open question` или `unverified risk`, а не как finding.
4. Компактизация должна сохранять приоритеты, а не усреднять все до одинаково важного списка.

## Ментальная модель

При compaction разбивай состояние ревью на 6 корзин:

1. `Scope` — что именно ревьюится и какие границы установлены пользователем.
2. `Checked` — какие зоны уже проверены и какой verdict по ним.
3. `Findings` — уже подтвержденные замечания с severity.
4. `Open risks` — что еще выглядит подозрительно, но требует проверки.
5. `Active skills` — какие доменные skills уже были нужны и почему.
6. `Next pass` — что проверять дальше в первую очередь.

Если в summary нет хотя бы этих 6 корзин, следующий проход легко теряет нить ревью.

Если использовались sub-agents, считай их вывод частью `Checked`/`Open risks`, но не смешивай сырые sub-agent hypotheses с confirmed findings.

## Рабочий процесс

### 1) Останови разрастание истории

1. Не тащи в compact summary весь путь рассуждений целиком.
2. Выкидывай повторяющиеся объяснения, промежуточные чтения и устаревшие гипотезы.
3. Оставляй только state, который нужен следующему проходу.

### 2) Зафиксируй границы ревью

1. Коротко запиши, что именно пользователь просил проверить.
2. Если поверхность ревью уже была ограничена пользователем, зафиксируй это явно.
3. Если используется дефолт `current branch vs main`, тоже зафиксируй это явно.

### 3) Сверни уже проверенные зоны

Для каждой большой зоны используй короткий verdict:

1. `checked, no findings` — проверено и сильных проблем нет.
2. `checked, findings recorded` — проверено, замечания уже зафиксированы.
3. `partially checked` — зона просмотрена не до конца.
4. `not checked yet` — сюда еще не заходили.

Не нужно переносить в compact summary весь подробный reasoning по каждой зоне.

### 4) Сверни findings

1. Для каждого finding сохраняй только:
   - severity;
   - место проблемы;
   - суть нарушения;
   - ожидаемое последствие.
2. Не переноси длинный текст формулировки, если он не нужен для продолжения ревью.
3. Если finding уже окончательно подтвержден, маркируй его как `confirmed`.
4. Если finding зависит от дополнительной проверки, перенеси его в `open risks`, а не в финальный список findings.

### 5) Сверни непроверенные риски

1. Сохраняй только high-signal вопросы, которые реально надо проверить.
2. Каждый open risk формулируй как проверяемый вопрос, а не как размытую тревогу.
3. Примеры хороших формулировок:
   - "нужно проверить, уходит ли новое состояние в component state";
   - "нужно проверить, не ломает ли diff prediction gating на клиенте";
   - "нужно проверить, можно ли вынести эту ванильную правку в `_Sunrise` partial".

### 6) Сохрани активированные skills

1. Перечисли только те skills, которые реально уже потребовались.
2. Рядом коротко укажи, зачем каждый был нужен.
3. Не дублируй полную карту выбора skills из основного review skill.

### 7) Сформируй `next pass`

1. Укажи 3-7 следующих проверок в порядке приоритета.
2. Ставь сначала то, что может поднять severity до `critical/high`.
3. Если findings уже достаточно для ответа пользователю, так и напиши: `готово к финальной формулировке`.

## Формат compact summary

Используй стабильный формат:

```text
Review scope:
- ...

Checked:
- зона A: checked, no findings
- зона B: checked, findings recorded

Confirmed findings:
- high: ...
- medium: ...

Open risks:
- проверить ...

Active skills:
- ss14-netcode: ...
- ss14-upstream-maintenance: ...

Next pass:
1. ...
2. ...
3. ...
```

Если ревью очень длинное, можно добавить еще блок `Discarded hypotheses`, но только если это помогает не возвращаться к уже опровергнутым версиям.

## Что обязательно сохранить

1. Границы ревью.
2. Уже подтвержденные findings и их severity.
3. Какие зоны уже проверены и с каким статусом.
4. Открытые вопросы, которые еще требуют чтения кода.
5. Какие доменные skills уже были нужны.
6. Следующие шаги.

## Что нужно выбрасывать

1. Повторяющиеся объяснения одной и той же проблемы.
2. Полные листинги кода, если достаточно короткой ссылки на суть.
3. Инструментальный шум: перечень всех поисков, чтений и мелких промежуточных шагов.
4. Гипотезы, которые уже опровергнуты и больше не влияют на план.
5. Stylistic рассуждения, если ревью сфокусировано на behavioral risk.

## Паттерны хорошей компактизации ✅

1. Сохранять только state, нужный следующему проходу.
2. Отделять confirmed findings от open risks.
3. Коротко фиксировать, что уже проверено и больше не требует возврата.
4. Переводить размытые опасения в проверяемые next-step вопросы.
5. Сохранять активированные skills, чтобы не потерять доменный контекст.
6. После compaction продолжать ревью с `Next pass`, а не начинать заново.

## Анти-паттерны компактизации ❌

1. Сжимать ревью в абстрактный пересказ без конкретных findings.
2. Смешивать confirmed findings и непроверенные гипотезы.
3. Терять границы пользовательского запроса.
4. Удалять сведения о том, что уже проверено, и потом читать те же зоны заново.
5. Пытаться сохранить весь reasoning вместо полезного summary-state.
6. После compaction заново пересматривать уже закрытые вопросы без причины.

## Практические примеры

### Пример 1: хороший compact state

```text
Review scope:
- staged changes only

Checked:
- BUI state sync: checked, findings recorded
- localization: checked, no findings
- upstream-risk in vanilla file edits: partially checked

Confirmed findings:
- high: новое поле меняется без Dirty/component state update

Open risks:
- проверить, можно ли вынести ванильную правку в `_Sunrise` partial

Active skills:
- ss14-ui-bui: проверка state/message контракта
- ss14-upstream-maintenance: оценка merge-risk

Next pass:
1. дочитать ванильный файл вокруг hook
2. проверить релевантные тесты на BUI
```

Комментарий: этого достаточно, чтобы безопасно продолжить ревью без полного повторного чтения истории.

### Пример 2: плохой compact state

```text
Мы посмотрели много файлов, вроде есть какие-то проблемы с синхронизацией и, возможно, с UI.
Надо потом еще раз все перечитать.
```

Комментарий: такой summary не сохраняет ни findings, ни plan, ни границы ревью.

### Пример 3: правильное отделение hypothesis от finding

```text
Confirmed findings:
- medium: используется obsolete API

Open risks:
- проверить, не пропущен ли prediction gating в client path
```

Комментарий: неподтвержденный риск не должен попадать в финальные findings раньше времени.

## Мини-чеклист перед завершением

1. В summary сохранены scope, checked, findings, open risks, active skills и next pass.
2. Подтвержденные findings отделены от hypotheses.
3. Нет лишних листингов кода и инструментального шума.
4. Следующий проход ревью можно начать по compact summary без повторного старта с нуля.

## Правило расширения skill

1. Не превращай этот skill в общий skill про code review.
2. Добавляй сюда только техники сжатия состояния ревью.
3. Если появятся особые паттерны для PR review, staged review или quick review, добавляй их как compaction-specific heuristics, а не как дубликат основного review workflow.
