# SS14 Code Review Quick

## Цель

Используй этот skill для быстрого risk-triage по изменениям в данном репозитории.
Его задача: быстро отфильтровать самые важные проблемы и выдать компактный результат в стабильном формате, не раздувая ответ лишней теорией 🙂

Если нужен полный архитектурный проход, глубокая проверка edge-cases и разворот reasoning по всем подсистемам, переключайся на `ss14-code-review`.

Если ревью становится слишком длинным и начинает упираться в окно контекста, подключай `ss14-code-review-context-compaction` и сжимай накопленное состояние ревью перед следующим проходом.

Если нужен быстрый read-only сбор контекста по большому diff, используй sub-agent `Explore`, чтобы вынести первичный поиск файлов, usages и тестов из основного short-pass.

## Когда использовать

Используй этот skill, когда:

1. Пользователь явно просит быстрое, короткое или предварительное ревью.
2. Нужно быстро отсортировать `critical/high` риски до более глубокого прохода.
3. Дифф небольшой, а пользователю важен короткий actionable-ответ.
4. Нужно сделать first-pass перед отдельным fix-pass.

Не используй этот skill как замену полному ревью для крупных PR, cross-cutting изменений или сложных regression-исследований.

## Источник правды и границы доверия

1. Источник правды номер один: выбранная пользователем поверхность ревью и актуальный код вокруг нее.
2. Следуй тем же правилам объема, что и в `ss14-code-review`: не расширяй поверхность ревью без запроса.
3. Даже в быстром режиме обязательно подключай релевантные доменные skills по diff, но ограничивайся теми, которые реально нужны для risk-triage.
4. В быстром ревью не пересказывай diff и не превращай ответ в длинный аудит.

## Ментальная модель

Думай о quick review как о трех коротких проходах:

1. `Scope`: что именно ревьюим и где границы.
2. `Risk`: какие 1-5 проблем реально опасны для поведения, валидации, mergeability, prediction, networking или UX.
3. `Signal`: что нужно сообщить пользователю прямо сейчас, а что можно оставить для полного ревью.

## Рабочий процесс

### 1) Зафиксируй поверхность ревью

1. Прочитай запрос пользователя и ограничься указанной областью.
2. Если пользователь просит проверить только текущие изменения, staged changes, конкретный diff или список файлов, ревьюй только это.
3. Если пользователь просит просто `quick review` без уточнения, используй дефолт `current branch vs main`.
4. Раздели затронутые файлы на группы и быстро оцени, какие подсистемы реально затронуты.
5. Если даже для короткого прохода файлов слишком много, сначала отправь в `Explore` задачу на быстрый read-only triage и вернись с компактной картой риска.

### 2) Подключи минимально достаточные skills

1. Выбери только те skills, без которых есть риск дать ложный verdict.
2. Для `Content.Shared` почти всегда проверяй networking/prediction последствия.
3. Для ванильных и сторонних файлов всегда держи в голове `ss14-upstream-maintenance`.
4. Для тестовых изменений или отсутствия покрытия учитывай `ss14-tests-authoring`.

## Sub-agent workflow

В quick review sub-agent полезен только для ускорения короткого triage.

1. Зови `Explore`, когда нужно быстро понять, какие файлы и usage paths вообще стоит смотреть.
2. Требуй от него короткий read-only результат: рискованные файлы, связанные вызовы, возможные tests, ключевые вопросы.
3. Не отдавай sub-agent финальный quick verdict: компактный ответ пользователю должен формироваться в основном потоке.

### 3) Сделай быстрый архитектурный проход

Ищи только high-signal проблемы:

1. Сломанная или отсутствующая серверная валидация.
2. Явный build/runtime breakage.
3. Потерянный `Dirty`, state sync, PVS/prediction gating.
4. Крупный merge-risk из-за ненужной правки ванильного/стороннего файла.
5. Логический дефект механики, который заметно ломает UX или дает абуз.

### 4) Проверь evidence ровно настолько, насколько нужно для triage

1. Если релевантные тесты уже есть, проверь, затрагиваются ли их предпосылки.
2. Если новая механика пришла без тестов, пометь это как testing gap, но не раздувай замечание выше реального риска.
3. Если проблема спорная и требует длинного расследования, не выдумывай finding: лучше пометь как residual risk или предложи full review.

### 5) Сформируй короткий ответ

1. Выводи findings строго по шкале `critical/high/medium/low/style`.
2. Старайся ограничиться 1-5 главным пунктами.
3. Если серьезных findings нет, скажи это явно и кратко перечисли testing gaps или residual risks.
4. Summary держи очень коротким: 1-3 предложения максимум.

## Формат ответа

Используй стабильную короткую форму:

1. Findings first.
2. Для каждого finding:
   - severity;
   - место проблемы;
   - краткая причина;
   - краткое последствие.
3. Затем короткий блок `Residual risks / Testing gaps`, если он нужен.
4. Потом одна короткая summary-фраза.

Не добавляй длинный changelog diff и не пересказывай весь код.

## Шкала severity

Используй ту же шкалу, что и в полном skill:

1. `critical` — гарантированная поломка, абуз через отсутствие валидации, build/runtime crash-class issues.
2. `high` — заметная логическая ошибка механики, сломанный UI, серьезный behavioral дефект.
3. `medium` — рискованные практики, `[Obsolete]`, неоптимальные решения, проблемы поддерживаемости.
4. `low` — мелкие smells и небольшие улучшения качества.
5. `style` — чисто stylistic замечания без behavioral impact.

## Паттерны хорошего quick review ✅

1. Сразу отсекать низкосигнальные замечания и оставлять только реально важное.
2. Сначала определять объем ревью, потом проверять риски.
3. Для маленького diff не устраивать giant-audit.
4. Для `Content.Shared` быстро проверять sync/prediction even в коротком режиме.
5. При правках ванильных файлов сразу оценивать merge-risk и возможность вынести логику в `_Sunrise`/`partial`.
6. Явно говорить, когда нужен полный follow-up review.
7. Использовать `Explore` для ускоренного triage больших diff, но не делегировать ему итоговую оценку severity.

## Анти-паттерны quick review ❌

1. Писать длинный полный аудит под видом quick review.
2. Игнорировать доменный skill только потому, что ревью "быстрое".
3. Снижать severity ради краткости ответа.
4. Раздувать `style`-замечания и забивать ими short output.
5. Самовольно ревьюить лишние файлы вне заданной поверхности.
6. Делать категоричные выводы там, где нужен deeper investigation.
7. Тратить quick-review на ручной перебор большой файловой поверхности вместо короткого sub-agent triage.

## Практические примеры

### Пример 1: хороший quick finding

```text
critical: сервер меняет новое состояние компонента, но не валидирует входящее значение от клиента.
Игрок сможет отправить некорректные данные и обойти механику проверки на сервере.
```

Комментарий: коротко, по делу, с явным behavioral impact.

### Пример 2: хороший quick verdict без findings

```text
Серьезных findings не вижу.
Residual risk: изменения затрагивают существующий BUI state contract, а отдельного regression test не видно.
```

Комментарий: быстрый ревью не обязан выдумывать замечания, если сильного сигнала нет.

### Пример 3: когда отправлять в full review

```text
high: diff меняет shared/client/server части движения одновременно.
Быстрый проход уже показывает риск prediction-регрессии; здесь нужен полный review с проверкой runtime-инвариантов.
```

Комментарий: quick review может честно эскалировать сложный кейс вместо поверхностного verdict.

## Мини-чеклист перед завершением

1. Поверхность ревью не расширена без запроса пользователя.
2. Проверены только high-signal зоны.
3. Findings не засорены stylistic шумом.
4. Если серьезных проблем нет, названы residual risks или testing gaps.
5. Если кейс слишком сложный для short-pass, это честно отмечено.

## Правило расширения skill

1. Не тащи сюда полную теорию ревью: для этого уже есть `ss14-code-review`.
2. Добавляй только quick-review heuristics и устойчивый формат short output.
3. Новые типовые failure modes добавляй только если они хорошо работают именно в triage-режиме.
