# SS14 Code Review Fix Pass

## Цель

Используй этот skill после ревью, когда нужно превратить findings в минимальные и корректные правки.
Главная задача: закрыть реальные замечания, не устроив ненужный rewrite и не ухудшив mergeability репозитория 🙂

Для read-only проверки call sites, usages, tests и соседних инвариантов перед фиксом можно использовать sub-agent `Explore`, но решение о самом патче и его валидации должно оставаться в основном потоке.

## Когда использовать

Используй этот skill, когда:

1. Пользователь просит исправить замечания code review.
2. Есть список findings из PR, review tool или ручного ревью.
3. Нужно сделать follow-up patch после triage/full review.
4. Нужно проверить, какие замечания валидны, а какие спорны или уже неактуальны.

Не используй этот skill для первичного исследования diff с нуля: сначала нужен review-pass.

## Источник правды и границы доверия

1. Источник правды номер один: сами findings и актуальный код вокруг них.
2. Review comment не равен истине автоматически: сначала проверь, воспроизводится ли проблема в текущем состоянии кода.
3. Исправляй root cause, но не расширяй diff без необходимости.
4. Для правок в сторонних/ванильных файлах держи приоритет mergeability и правила `ss14-upstream-maintenance`.

## Ментальная модель

Думай о fix-pass как о пяти шагах:

1. `Normalize`: понять, что именно утверждает finding.
2. `Validate`: проверить, что проблема реальна и не уже закрыта.
3. `Scope`: определить минимально достаточное исправление.
4. `Patch`: внести точечные изменения с учетом доменных skills.
5. `Verify`: убедиться, что фикс закрыл проблему и не добавил новую.

## Рабочий процесс

### 1) Нормализуй входные замечания

1. Разбей findings по severity и по файлам/подсистемам.
2. Для каждого finding явно сформулируй:
   - что сломано;
   - где это проявится;
   - какой контракт нарушен.
3. Если замечание расплывчатое, сначала сделай его проверяемым, а уже потом исправляй.

### 2) Проверь корректность finding

1. Убедись, что проблема все еще существует в текущем коде.
2. Если finding устарел, конфликтует с актуальной логикой или основан на неверной предпосылке, не чини его слепо.
3. Если замечание спорное, сформулируй это явно и отдели от реально подтвержденных дефектов.
4. Если для валидации finding нужно быстро собрать read-only контекст по usages, tests или смежным подсистемам, отдай этот поиск в `Explore`.

### 3) Выбери минимальное исправление

1. Сначала ищи локальный root cause, а не симптом.
2. Не раздувай change set: одна проблема не должна вести к ненужному рефакторингу половины системы.
3. Для ванильных и сторонних файлов оставляй только минимальные хуки и comment-marked правки, а новую логику выноси в `_Sunrise` и `partial`, когда это уместно.
4. Если можно исправить проблему без изменения публичного API, предпочитай это.

### 4) Подключи релевантные skills перед патчем

1. Для networking/prediction/PVS изменений подключай соответствующие доменные skills.
2. Для YAML/prototype fixes учитывай migration и все внешние ссылки на ID.
3. Для UI/BUI fixes проверяй симметрию server/client state-message контракта.
4. Для hot-path fixes учитывай `ss14-standard-optimizations`, чтобы не чинить одну проблему ценой новых alloc/regression.

### 5) Внеси исправление

1. Держи diff минимальным и целевым.
2. Сохраняй существующий стиль и архитектуру подсистемы.
3. Не исправляй рядом лежащие unrelated smells только потому, что они попались под руку.
4. Если finding требует большего перепроектирования, чем ожидалось, зафиксируй это и не маскируй большим тихим rewrite.

### 6) Проведи verify-pass

1. Проверь, что исходный механизм поломки действительно закрыт.
2. Проверь соседние инварианты: prediction, Dirty/state sync, event order, validation, mergeability.
3. Если в проекте есть релевантные тесты, учти их даже если тестовые файлы не менялись.
4. Если тестов нет, хотя фикс закрывает баг в новой механике, предложи добавить regression coverage.
5. Для player-visible изменений не забывай о changelog-требовании в PR-описании.

### 7) Сформулируй результат

1. Кратко перечисли, какие findings закрыты.
2. Отдельно укажи, какие замечания не исправлялись и почему: invalid, outdated, too broad, needs design decision.
3. Отдельно перечисли residual risks и testing gaps.

## Приоритеты по severity

Используй ту же шкалу, что и в `ss14-code-review`, но применяй ее к порядку фиксов:

1. `critical` — чинить в первую очередь и проверять наиболее строго.
2. `high` — чинить приоритетно, не откладывая без причины.
3. `medium` — чинить, если это реально входит в scope fix-pass.
4. `low` — брать только если это почти бесплатный и безопасный fix.
5. `style` — не должен раздувать fix-pass, если пользователь не просил styling cleanup отдельно.

## Паттерны хорошего fix-pass ✅

1. Сначала валидировать finding, потом писать код.
2. Исправлять конкретный контракт, а не косметический симптом.
3. Держать diff минимальным и объяснимым.
4. Для сторонних файлов минимизировать правки и выносить новую логику в `_Sunrise`/`partial`, когда это уместно.
5. После фикса проверять не только место бага, но и соседние runtime-инварианты.
6. Явно сообщать, если finding оказался спорным или неактуальным.
7. Предлагать regression test там, где он действительно стабилизирует фикс.
8. Использовать sub-agent для ускорения read-only verify-поиска, а не для делегирования самого исправления.

## Анти-паттерны fix-pass ❌

1. Чинить review comment как догму без проверки фактов.
2. Раздувать fix-pass в большой рефакторинг без прямого запроса.
3. Исправлять стиль кода вместе с behavioral bugfix и загрязнять diff.
4. Закрывать symptom, оставляя root cause на месте.
5. Игнорировать `ss14-upstream-maintenance` и переписывать ванильный файл целыми блоками.
6. После фикса не проверять prediction/networking/validation side-effects.
7. Молчать о том, что часть замечаний не была исправлена из-за scope или спорности.
8. Делегировать sub-agent самому выбор патча без собственной проверки reviewer/fixer-потоком.

## Практические примеры

### Пример 1: корректный minimal fix

```text
Finding: сервер меняет новое поле компонента, но не вызывает Dirty.
Fix-pass: добавить Dirty/state update в точке мутации и проверить, что клиентский UI получает новое значение.
```

Комментарий: это целевое исправление root cause, а не rewrite соседнего кода.

### Пример 2: правильный отказ от лишнего rewrite

```text
Finding: логика в ванильном файле стала слишком большой.
Fix-pass: оставить минимальный hook с comment-маркером, а новую ветку вынести в partial-часть под `_Sunrise`.
```

Комментарий: fix-pass должен улучшать mergeability, а не ухудшать ее.

### Пример 3: finding оказался невалидным

```text
Review comment утверждает, что валидации нет, но актуальный серверный путь уже проверяет входные данные до мутации состояния.
Fix-pass: не вносить ложный фикс, а явно отметить comment как outdated/invalid.
```

Комментарий: не каждая review-реплика должна кончаться кодом.

## Мини-чеклист перед завершением

1. Каждый finding сначала проверен на актуальность.
2. Исправления минимальны и не вышли за нужный scope.
3. Для сторонних файлов merge-risk не ухудшен.
4. Проверены соседние runtime-инварианты, а не только место фикса.
5. Явно отмечены residual risks, testing gaps и незакрытые комментарии.

## Правило расширения skill

1. Не превращай этот skill в общий skill про code review.
2. Добавляй сюда только паттерны post-review remediation.
3. Новые блоки включай только если они помогают делать fix-pass точнее, уже и безопаснее.
